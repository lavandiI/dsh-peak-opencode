## 0. Резюме

Проект в хорошем состоянии: маленький, без зависимостей и без сборочного шага, с осмысленными комментариями
и живым тестом, который действительно рендерит компоненты. Контракты DSH, на которые опирается плагин, я проверил
по исходникам установленного рантайма — все они существуют в этой версии (`conversation.input.dock`,
`plugins.bundle.config`, `data-composer-card`, `--dsw-radius-panel`, `ctx.effect(fn, label)`, `webServer.register({kind:'exact'})`,
`modelDirectories`, `locale`). Тестовая сюита проходит (`npm test`, 148 проверок), пакет собирается (27 файлов, 157.7 kB),
хостовая половина live отдаёт реальный каталог: `200`, `format=2`, **32 модели**, из них 2 с пиковыми окнами и 4 бесплатных.

Три вещи стоит поправить раньше остальных:

1. **Смена сессии** — полоса не переподписывается на модель новой сессии и продолжает показывать модель предыдущей
   (`lib/client.js:1739-1750`). Единственная найденная функциональная ошибка повседневного использования.
2. **Документация установки ссылается на URL, которого нет**: `/plugins/dsh-peak-opencode/client.js` отдаёт `404`
   в текущем DSH (`README.md:101`, `README-ru.md:97`, `PUBLISHING.md:26`). Проверено запросом к живому серверу.
3. **Точность цен**: `formatMoney` округляет всё до трёх знаков (`lib/client.js:1077-1084`), поэтому цена `< $0.0005`
   печатается как `$0.00`, а `$0.0028` — как `$0.003`. Второе видно прямо сейчас: в живом каталоге у
   `mimo-v2.6-flash` цена чтения из кеша `0.0028`, а полоса покажет `$0.003` (+7 %). Комментарий над функцией
   (`1075-1076`) обещает поддержку именно «дробных вроде $0.0028» — то есть код не делает того, что заявлено.
   Воспроизведено на реальной функции из файла.

**Статус:** все четыре пункта P0 (включая `PUBLISHING.md`), весь блок P1 и почти вся волна техдолга исправлены
в рабочем дереве, тесты добавлены до 206 проверок — см. §4. Версия поднята до `0.4.5`, запись в `CHANGELOG.md` есть,

### 2.1. Высокие

#### P1-1. При смене сессии полоса продолжает показывать модель предыдущей сессии

**Статус:** исправлено. Эффект больше не зависит от `store`, а перезапускается на `[props.ctx, props.sessionId]`
и каждый раз заново резолвит стор; в `test/render.cjs` добавлен сценарий «switching session re-subscribes to the new store».

**Где:** `lib/client.js:1748-1767`

```js
const [store, setStore] = react.useState(() => resolveModelStore(props.ctx, props.sessionId));
react.useEffect(() => {
    if (store !== null) return;            // ← выход, если стор уже найден
    ...
}, [store, props.ctx, props.sessionId]);
```

**Почему ошибка.** `props.sessionId` указан в зависимостях эффекта, то есть компонент рассчитывает, что сессия может
смениться без размонтирования. Но при смене сессии `store` уже не `null`, эффект выходит на первой строке и никогда не
перезапрашивает `resolveModelStore` для нового `sessionId`. Если хост переиспользует инстанс компонента между сессиями
(слот `conversation.input.dock` — `kind: 'list'`, `scope: 'session'`, без `key` по сессии в `ConversationContent.tsx:169`),
полоса показывает тариф и цену модели из другой сессии.

Важная оговорка: встроенный `ConversationContent` регистрируется как **фабрика** (`apply.ts:344-394`), и пересоздаёт ли
хост инстанс при смене сессии — из кода однозначно не следует. То есть баг условный. Но код объективно не готов к смене
`sessionId`, хотя сам объявляет её возможной, а цена ошибки — неверные деньги на экране. Проверяется вручную за минуту:
открыть сессию с `deepseek-v4.1-flash`, переключиться на сессию с `glm-5.3` и посмотреть, сменилась ли подпись тарифа;
именно этот сценарий и стоит добавить в регрессионный чек-лист.

**Как исправить** (перезапрашивать стор при смене сессии — 6 строк):

```js
react.useEffect(() => {
    const found = resolveModelStore(props.ctx, props.sessionId);
    if (found !== null) { setStore(found); return; }
    let tries = 0;
    const timer = window.setInterval(() => {
        const next = resolveModelStore(props.ctx, props.sessionId);
        if (next !== null) { setStore(next); window.clearInterval(timer); }
        else if ((tries += 1) >= RETRY_MAX) window.clearInterval(timer);
    }, RETRY_MS);
    return () => window.clearInterval(timer);
}, [props.ctx, props.sessionId]);
```

Альтернатива: в `apply` обернуть компонент в `key={sessionId}`, но тогда теряется смысл зависимостей в текущем эффекте.

#### P1-2. Документация установки обещает URL клиентской половины, которого не существует

**Статус:** исправлено. Формулировка заменена в `README.md`, `README-ru.md` и `PUBLISHING.md`; в `test/render.cjs`
добавлена проверка, что документы не обещают `/plugins/<пакет>/client.js` и упоминают текущую версию.

**Где:** `README.md:101`, `README-ru.md:97`, `PUBLISHING.md:26` — «DSH отдаёт клиентскую половину по
`/plugins/dsh-peak-opencode/client.js`».

**Проверка:**

```
GET http://127.0.0.1:52413/plugins/dsh-peak-opencode/client.js  → 404
GET http://127.0.0.1:52413/dsh-peak-opencode/models             → 200 (хостовая половина жива)
```

**Почему так.** В `@deepseek-ai/dsh-client-modules/src/index.ts:1262-1292` маршрут `/plugins` обслуживает только
`/plugins/<pkg>/assets/<path>`, рекламированные combo-URL из boot-графа, их `.map` и chunk-URL текущей ревизии;
всё остальное — `404`. Отдельного «per-plugin client.js» в этой версии нет: клиентская половина вклеивается в combo-скрипт
и грузится через `window.__DSH_BOOT__`.

**Почему важно.** Инструкция объясняет человеку, куда смотреть при отладке, и обещает несуществующий адрес. Для нового
контрибьютора это ложный след, для пользователя — «плагин не установился».

**Как исправить.** Заменить фразу на нейтральную: «DSH включает клиентскую половину в boot-граф страницы (combo-скрипт
`/plugins/...`); отдельного URL у плагина нет — после установки достаточно обновить страницу». Проверку в тесте
(`test/render.cjs:513-517`) расширить утверждением, что README не содержит `plugins/<pkg>/client.js`.

### 2.2. Средние

#### P2-1. Точность цен: `$0.0028` печатается как `$0.003`, а `< $0.0005` — как `$0.00`

**Статус:** исправлено. `formatMoney` печатает до четырёх знаков, а всё, что меньше `$0.0001`, отдаётся как `<$0.0001`
(знак «меньше» перед валютой); в `test/render.cjs` добавлены модели `mimo-v2.6-flash` (0.0028) и `nano-price` (0.00004).

**Где:** `lib/client.js:1078-1101` (`formatMoney` → `toFixed(4)`, хелпер `money`), используется в `priceParts` и `priceLabel`.

**Воспроизведено на реальной функции** (`artifacts/audit/probe.cjs` и точечный прогон по живым значениям каталога):

```
0.0004  -> 0.00      # цена есть, а показывается ноль
0.00049 -> 0.00
0.0005  -> 0.001
0.002   -> 0.002
0.0028  -> 0.003     # ← сейчас так у mimo-v2.6-flash (cacheRead = 0.0028)
```

`toFixed(3)` округляет, а не усекает, поэтому `0.0028` превращается в `0.003`: завышение на 7 % на самой «молодой»
цене каталога. Сегодня это затрагивает одну модель (`mimo-v2.6-flash`), и по мере удешевления кеша таких моделей будет больше.

**Как исправить:** не округлять до фиксированного числа знаков, а подбирать его по значению (до 4–5 знаков для
малых цен) и отдавать форматирование `Intl.NumberFormat` — см. также P3-2. Плюс защита от нуля:

```js
if (result > 0 && result < 0.00005) return "<0.0001";
```

#### P2-2. Множитель по дате молча теряется, если у модели есть и часовые окна

**Статус:** исправлено. Множители перемножаются: в пик действует окно × дата, в льготные часы — только дата
(она поднимает весь прайс). Тест `dual-multiplier` проверяет все три состояния.

**Где:** `lib/client.js` (`PeakBar`, расчёт `factor` и `sinceFactor`)

**Воспроизведено:** каталог-строка с `multipliers: [{date: {gte: '2026-12-01'}, factor: 2}, {utc_days+utc_hours, factor: 3}]`
даёт `peak: {days:['mon'], windows:[['01:00','04:00']], factor: 3}` **и** `since: {from: 1796083200000, factor: 2}`,
но `tariffFor` возвращает `kind: 'peak'`, и дата из расчёта выпадает.

Сейчас в каталоге таких моделей нет (`deepseek-*` — только окна, `gemini-4-argon` — только дата), поэтому дефект
латентный. Но формат каталога открытый, и первая же модель «окна + дата» будет посчитана неверно — без ошибки в консоли.

**Как исправить:** либо явно учитывать оба множителя (`factor = peak.factor * (now >= since.from ? since.factor : 1)`),
либо в `tariffFor` возвращать `kind: 'dated'` при наличии `since`, а окна применять внутри — но тогда нужно решить,
что показывать в подписи. Минимум — залогировать/пометить в настройках, что у модели два множителя и учтён один.

#### P2-3. Перевод окон UTC→Пекин не учитывает сдвиг суток

**Где:** `windowsOfPeak` (`lib/client.js:1622-1635`) переводит минуты в пекинские (`+8h`, с переносом через полночь),
а `daysOfPeak` (`1611-1618`) оставляет дни недели из **UTC** (`utc_days`). Пары «день + окно» при этом расходятся.

**Воспроизведено:** правило `days: ['mon'], windows: [['22:00','02:00']]` (UTC понедельник 22:00 = пекинский вторник 06:00)
даёт окно `[360,600]` (06:00–10:00) с днями `mon` — то есть фаза приезжает на сутки раньше.

У опубликованного правила DeepSeek окна целиком внутри UTC-суток (`01:00–04:00`, `06:00–10:00`), поэтому сегодня всё
верно. Это заложенная мина на случай, если провайдер сдвинет окна (например, на `23:00–03:00`).

**Как исправить:** хранить правило в UTC (дни + минуты UTC) и переводить в пекинское/локальное время только для подписи,
либо считать сдвиг дня на каждое окно (`Math.floor((start + 480) / 1440)`) и раскладывать дни по окнам.

#### P2-4. Неудачный `refresh` переводит хост в `ok:false`, хотя снимок валиден — клиент уходит мимо кеша

**Статус:** исправлено. `ok` теперь означает «есть данные», добавлено поле `stale`; клиент принимает снимок и
показывает в настройках «Показан снимок от …» вместо «Каталог не загрузился». Покрыто тестами хоста (`stale`,
холодный старт без сети) и клиента (ответ хоста со `stale: true`, упавшее обновление при живом кеше).

**Где:** `lib/index.js` (`snapshot`), `lib/client.js` (`fetchCatalog`, `catalogStore.load`, блок предупреждения в настройках)

**Что происходит.** Загрузились успешно, через 6 часов автообновление упало (сеть, 5xx у opencode.ai) — хост продолжает
отдавать валидные данные, но с `ok:false`. Клиент считает такой ответ непригодным, идёт напрямую в
`https://opencode.ai/...` (где, скорее всего, тоже ошибка) и переводит стор в `stale`. Полезный кеш хоста оказывается
невостребованным, а в настройках показывается ошибка при живых данных.

**Как исправить:** в снимке разделить «данные есть» и «последняя попытка не удалась» (`ok: models.length > 0`,
`stale: error !== null`, `error` — как текст предупреждения), а в клиенте падать в публичный эндпоинт только при
`ok === false` **и** пустом `models`.

#### P2-6. Клиент не обновляет каталог сам

**Где:** `lib/client.js` (`apply`, блок `dsh-peak-opencode: catalog refresh`)

#### P2-7. Настройки живут только в `localStorage`

**Статус:** закрыто решением. Переезд в конфигурацию DSH (`config` в `cordis.patch.yml` + `export const Config`) —
отдельная задача с миграцией уже сохранённых настроек; пока поведение зафиксировано как ограничение в обоих README:
настройки лежат в браузере, в другом браузере или на другой машине они свои.

**Где:** `lib/client.js` (`STORE_KEY`, `settingsStore`), `README.md`, `README-ru.md`

Свой CSS и переопределённые окна не синхронизируются между браузерами и машинами, теряются вместе с данными сайта и не
попадают в профиль DSH. Для плагина, у которого уже есть панель в `plugins.bundle.config`, логичнее хранить конфигурацию
штатным механизмом DSH (строка `config` в `cordis.patch.yml` + `export const Config`), а `localStorage` оставить только
как быстрый кеш. Это ещё и снимает вопрос «почему на другой машине другой цвет».

Если решение осознанное — стоит написать это в `SECURITY.md`/README как ограничение (сейчас там об этом ни слова).

#### P2-8. `role="status"` с меняющимся `aria-label` — постоянная болтовня скринридера

#### P2-10. Побочный эффект в рендере: `directory.load()` вызывается из `resolveModelStore`

**Статус:** исправлено. Загрузку просит `requestModelDirectory` из эффекта (и из ретрай-цикла), рендер остаётся чистым.
Тест «the model directory is loaded once per mount, not per render».

**Где:** `lib/client.js` (`requestModelDirectory`, эффект `PeakBar`)

Загрузка в рендере — то, чего React не любит: в `StrictMode` рендер вызывается дважды, и запрос уйдёт дважды (тут он
дедуплицируется внутри DSH, но полагаться на это не стоит). Плюс `MutationObserver` создаётся из `useDshLocale()`
(`884-887`) во время рендера.

**Как исправить:** перенести вызов `directory.load()` в `useEffect` (он всё равно есть — просто добавить там `load()`),
а `localeStore.bind` вызвать один раз в `apply`, а не в хуке.

### 2.4. Безопасность

Отдельных уязвимостей не нашёл. Проверено:

- **Инъекций нет:** в `lib/` нет `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write`
  (поиск по обоим файлам). Данные каталога попадают только в текстовые узлы и в `aria-label`/`title`.
- **Секретов нет**, `postinstall`/build-скриптов нет, зависимостей нет (только React от DSH и стандартная библиотека Node).
- **Маршрут `/dsh-peak-opencode/models`** отдаёт только публичный каталог, без данных профиля. Если DSH слушает не loopback
  (настраивается в `dsh-host-webserver`), маршрут доступен по сети — данные не секретные, но `?refresh=1` из P2-5 стоит
  ограничить именно из-за этого.
- **Пользовательский CSS** инжектится в `document.head` без скоупа — это осознанное решение (пользовательский код, как
  userscript), и оно описано в `SECURITY.md:27`. Импортированные извне настройки теоретически могут тянуть внешние URL
  через `url(...)`; риск низкий.
- **Парсинг каталога** устойчив: `normalizeModel` отбрасывает строки без строкового `id`, всё остальное приводит к `null`;
  битый JSON ловится `try/catch`.
